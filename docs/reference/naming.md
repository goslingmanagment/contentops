# Имена контента: правила и примеры

Нормативное приложение к [SPEC](../../SPEC.md) для реализации и проверки нейминга.
Разделы 1–9 и 11 содержат детальный контракт; раздел 10 — проверочные сценарии.
SPEC остаётся главным документом при конфликте. Этот файл сохраняет обоснования, точные
форматы и примеры, чтобы за ними не приходилось идти в историю Git.

Исторические нотации, полный реестр PPV и правила импорта находятся отдельно в
[«Старый контент и импорт»](legacy-and-import.md). При расхождении со SPEC действует SPEC;
неразрешённые конфликты остаются неразрешёнными.

## 1. Зачем нужна конвенция

Главное правило: **до появления софта люди ничего нового руками не поддерживают**.
Модель продолжает загружать файлы и писать короткий отчёт в Telegram привычным способом.
Не нужны новые папки, ручные ID, переименование, промежуточная таблица или отдельный
реестр.

Конвенция строится на следующих принципах:

1. Идентичность задают ID, модель и связь с байтами. Имя и путь — производные.
2. Люди задают смысл: тип, русское название и подтверждение неоднозначностей (подтверждать
   может и агент, SPEC §11.1). Имена
   генерирует система.
3. Нулевая дисциплина — поддерживаемый режим. Даже без ручного названия система может
   создать объект с ID, техническими метаданными и временным названием-заглушкой.
4. Для каждого класса имени существует одна грамматика и один разборщик.
5. ID удобно произносится по-русски без ведущих нулей: «ппв 73», «сет 70»,
   «кастом 181», «фуп 412».
6. Статусы, даты использования, размещения и имена фанов не кодируются в канонических
   именах.
7. Канонические машинные имена используют ASCII; русский смысл остаётся в БД и UI.
8. Старые имена и пути навсегда сохраняются как алиасы.
9. ID виден операторам, но не попадает в подписи, тексты постов и сообщения фанам.
10. Имя или ник покупателя виден в карточке и списке заказов по обычным правам доступа;
   он не подставляется в имена файлов, названия альбомов vault, подписи и промо-пакеты.
11. Яндекс.Диск остаётся источником и raw-архивом модели; штатный процесс ContentOps его
   не перестраивает.

Прежние схемы ломались, потому что делали человека движком переименований и хранили
изменяемые факты в именах. После смены ответственного сохранялись только простые ID и
папка на единицу; даты, `used`, длительность, превью и реестры переставали обновляться.

## 2. ID объектов

```text
ID := TYPE "-" NUMBER
TYPE := PPV | SET | SXT | CUS | FYP | LIFE | RAW | PRM
```

| Тип | Объект | Минимальный паддинг | Устная форма |
|---|---|---:|---|
| `PPV` | PPV-релиз или бандл | 3 | «ппв 76» |
| `SET` | фотосет одной съёмки | 3 | «сет 70» |
| `SXT` | упорядоченный секстинг | 3 | «секстинг 13» |
| `CUS` | сданный кастом: видео или фотосет | 3 | «кастом 181» |
| `FYP` | самостоятельный монтаж ленты | 4 | «фуп 412» |
| `LIFE` | один лайф-объект из 1…N файлов | 3 | «лайф 36» |
| `RAW` | пачка сырья | 4 | «съёмка 34» |
| `PRM` | промо-подборка в папке канала | 3 | «промо 12» |

Правила ID:

- Счётчики раздельны по модели и типу. Бизнес-ключ — `(model, type, number)`.
- У новой модели каждый тип начинает свой ряд с единицы с паддингом из таблицы:
  `001`, для FYP и RAW — `0001`.
- Модель не входит в произносимый ID. `ari/PPV-001` допустим как машинный путь или
  письменное уточнение, но не как каноническое имя.
- Каноническая письменная форма всегда содержит паддинг типа; ведущие нули опускаются
  только в речи и неряшливом пользовательском вводе.
- Машины всегда получают модель явно. API и агент не угадывают её по голому ID.
- Бот, закреплённый за моделью, показывает её рядом с ID. Без модельного контекста он
  спрашивает пользователя, а не выбирает сам.
- Паддинг — минимум, а не предел: после `PPV-999` идёт `PPV-1000`.
- Парсер принимает 1–6 цифр и неряшливые формы `ppv73`, `PPV 73`, `ппв-73`,
  `[PPV-073]`; сортировка всегда числовая.
- Номер выдаёт только система, транзакционно. Он не переиспользуется. Удалённый объект
  оставляет tombstone; при слиянии младший ID остаётся, второй становится алиасом.
- `CUS` выдаётся при принятии сданного кастома (SPEC §4.1). Заказ ведёт агент по API;
  у заказа нет публичного ID, его внешняя ссылка — `tg:<chat>/<topic>/<message_id>`.
  Старые Telegram-карточки связываются со сданными кастомами при импорте.
- Файл внутри объекта получает под-хендл, а не отдельный публичный ID:
  `SET-069/ed07`, `PPV-073/teaser`, `RAW-0034/raw12`.
- Категория сырья, дата, длительность и модель не входят в ID. `BG` — тег жанра, а не
  отдельный тип или префикс. Назначение RAW определяется источником и подтверждаемыми
  метаданными, а не номером.

Отвергнуты номера без паддинга, даты в номере, сквозной агентский ряд, модель внутри ID,
буквенные суффиксы, фиксированные шесть цифр, общие счётчики всех моделей,
непересекающиеся номерные блоки и отдельный каталог на каждую модель. Они либо ломают
сортировку и устную работу, либо создают несколько правил вместо одного.

Разовый сдвиг легаси-ряда PPV, записанный 24–27.08, снят 04.09.2026: ряд не двигается,
Я.Диск не переименовывается, коллизии решаются номерами в системе (SPEC §6.4). История
решения — в
[«Старый контент и импорт»](legacy-and-import.md#5-доказательства-и-записанный-сдвиг-ppv).

## 3. Объекты, роли и версии

| Объект | Основные роли файлов |
|---|---|
| `RAW` | `raw01…` по времени съёмки |
| `PPV` | `master`, `teaser`, `pic01…`, `thumb` |
| `SET` | `raw01…`, `ed01…`; видео в папке сета требует разбора при приёмке (PRD §5) |
| `SXT` | `pic01…`, `clip01…`; исходный порядок имеет смысл |
| `CUS` | `master`, `pic01…`; пересдачи становятся версиями |
| `FYP` | `master`, уникальные версии `u1…`; родители хранятся отдельно |
| `LIFE` | `pic01…`, `clip01…` |
| `PRM` | подборка ассетов и ссылок на существующие ассеты, канал, подрядчик; состав каждой передачи фиксируется отдельно (§6) |

Отдельного публичного ID не получают кадр, сырой файл внутри RAW, сториз,
vault-альбом, размещение, задача и элемент очереди. Бандл остаётся PPV, а не отдельным
типом.

Номер `PRM` сохраняется при пополнении подборки и повторных передачах (решение
06.09.2026, SPEC §7.1). Добавление существующего ассета в промо не меняет его ID и
исходный объект. У специально снятых для промо файлов используются обычные роли
`pic01…` и `clip01…` внутри `PRM`. У передачи — внутренний ключ; нового публичного
номера ей не присваивают.

Закрытый словарь ролей:

```text
master teaser preview pic raw ed clip thumb cap
```

- Порядковая роль получает `01…`: `pic01`, `raw07`, `ed03`.
- Исторические подпапки `optional/` и `extra/` у секстинга становятся тегами и не
  создают новые роли.
- Первая версия не имеет суффикса; переделка того же результата получает `_v2`.
- Уникальная версия FYP — отдельный ассет с под-хендлом `uN`; в имени скачивания
  токен `_uN` стоит перед `_vN`: `FYP-0012_slug_master_u2.mp4`, её переделка —
  `FYP-0012_slug_master_u2_v2.mp4`; точный адрес — `/a/FYP-0012/u2/v2` (решение
  08.09.2026). Отсутствие `_uN` — базовый монтаж, отсутствие `_vN` — версия 1.
- Самостоятельный новый монтаж получает новый `FYP`, а не новую версию старого.
- Несколько монтажей могут иметь один источник; один монтаж может иметь несколько
  размещений без копирования байтов.
- Кастом и выпущенный из него PPV — разные объекты над общим блобом или связанными
  версиями. Эксклюзивности нет: PPV можно сделать из любого кастома (решение 29.08.2026).

## 4. Название, slug и теги

- **Название** — русский текст из 2–4 крючков: одежда, действие, место. Например:
  «Йога, дилдо, сквирт» или «Красное платье, зеркало, отель».
- **Короткое английское название** (`title_en`) — необязательное поле объекта:
  2–5 слов, словарь как в хэштегах vault (`titfuck`, `dildo-ride`, `boob-slaps`).
  При приёмке ИИ предлагает его вместе с русским названием; утверждает человек или
  агент. До подключения ИИ поле заполняется вручную и не блокирует приёмку.
- **Slug** не хранится: вычисляется в момент скачивания (решение владельца
  04.09.2026). Источник — текущее короткое английское название, если оно заполнено;
  иначе русское название (решение владельца 18.10.2026). Для русского — прежний
  фиксированный транслит:
  `ё→e й→i х→kh ц→ts ч→ch ш→sh щ→sch ъ→∅ ь→∅ ю→yu я→ya ы→y`; стоп-слова удаляются.
- Английские стоп-слова: `a, an, and, as, at, by, for, from, in, into, of, on, or,
  the, to, with, without`; для транслита действует список от 28.09 в §11.
- Slug начинается с буквы, содержит до пяти слов и 40 символов, использует строчные
  ASCII-слова через `-`. Поменялось название, из которого строится slug, — изменилось
  имя следующего скачивания; ID, URL и блоб прежние.
- Фан, имя модели, аккаунт, дата и статус в slug не попадают.
- Три группы тегов сохраняются: действия, атрибуты, настроение (решение владельца
  06.09.2026; PRD §5, SPEC §8.3). Группа известного тега задана в общем словаре;
  свободный тег допустим без группы. КМ вводит теги общей строкой и может открыть
  просмотр по группам. ИИ предлагает, утверждает человек или агент (SPEC §2.1 п. 9). Группировка из старого
  PPV-реестра сохраняется при импорте.
- `platform_title` — отдельное продающее название для конкретной платформы и аккаунта.
  Это не каноническое название и не имя vault-альбома.

## 5. Грамматика имён

```text
SLUG := [a-z][a-z0-9]*("-"[a-z0-9]+)*
ROLE := master|teaser|preview|pic|raw|ed|clip|thumb|cap
ORD  := [0-9]{2,3}

download := ID[_slug]_role[NN][_uN][_vN][__account_YYYY-MM-DD[_HHMM]][__NmSSs].ext
```

Имена с ID существуют только у скачиваний и экспортов: физических папок и файлов с ID в
хранилище нет (SPEC §9.1). Опорные регулярные выражения:

```regex
EXPORT     ^(?P<id>(?:PPV|SET|SXT|CUS|FYP|LIFE|RAW|PRM)-\d{3,6})(?:_(?P<slug>[a-z][a-z0-9]*(?:-[a-z0-9]+)*))?_(?P<role>master|teaser|preview|pic|raw|ed|clip|thumb|cap)(?P<ord>\d{2,3})?(?:_u(?P<uniq>[1-9]\d*))?(?:_v(?P<version>[2-9]|[1-9]\d+))?(?:__(?P<account>[a-z0-9]+-[a-z0-9]+)_(?P<date>\d{4}-\d{2}-\d{2})(?:_(?P<hhmm>\d{4}))?)?(?:__(?P<dur>\d+m\d{2}s))?\.(?P<ext>[a-z0-9]{2,4})$
ID_LOOSE   (?i)\b\[?(?P<type>PPV|SET|SXT|CUS|FYP|LIFE|RAW|PRM)\s*[-_ ]?\s*(?P<num>\d{1,6})\]?\b
```

В поиске и resolve тип в `ID_LOOSE` принимается и в устной форме из §2 («ппв 73»,
«фуп 412», «съёмка 34»), регистр и «ё» не важны; имена файлов и альбомов vault
разбираются только с латинским типом.

Slug не содержит `_` и начинается с буквы, поэтому поля разбираются однозначно.
Роль обязательна всегда. Версия 1 не имеет суффикса; для последующих версий `N >= 2`.
Один парсер принимает обе формы: суффикс назначения целиком необязателен, аккаунт
без даты и дата без аккаунта не выдаются. Примеры и исключения — в §6.

Политики имён:

- В обычном скачивании из карточки аккаунта и даты нет. Суффикс назначения добавляется
  только при скачивании из строки плана; дата в нём — плановая, в формате ISO.
- Длительность есть только в UI и, для PPV/кастомов, в имени скачивания.
- Расширение приводится к нижнему регистру: `.MOV→.mov`, `.JPG/.jpeg→.jpg`; `.heic`
  сохраняется. `.mov` нельзя просто переименовать в `.mp4` без транскодирования.
- Допустимы только `[A-Za-z0-9._-]`. Запрещены пробелы, кириллица, скобки,
  двоеточия, запятые, `+`, длинное тире и двойные расширения.
- Префикс ID пишется прописными, остальные машинные токены — строчными; сравнение имён
  выполняется без учёта регистра.
- Inbox-имена нормализуются в NFC. Алиасы хранятся в NFC и сравниваются без учёта
  регистра.
- Лимит имени скачивания — 100 символов.

## 6. Скачивание и экспорт

Физического пути с ID нет: байты лежат в `blobs/` по SHA-256, связь ID → роль → блоб
хранит Postgres ([SPEC §9.1](../../SPEC.md#9-хранилище-и-медиа)). Человекочитаемое имя
существует только в момент скачивания: сервер собирает его по §4 и отдаёт
в `Content-Disposition`. Старые пути и имена Я.Диска живут в БД как SourceObject и
Alias, по ним объект находится поиском.

**Из карточки каталога** имя содержит ID, slug из названия, роль и при необходимости
номер файла, версию и длительность. Аккаунт и дата не запрашиваются и не подставляются
из других размещений объекта (решение владельца 06.09.2026):

```text
FYP-0412_yoga-mirror_master.mp4
FYP-0412_yoga-mirror_master_v2.mp4
SET-069_red-dress_ed03.jpg
```

**Из строки плана** к тому же имени добавляются аккаунт, плановая дата и при
необходимости время слота — автоматически из выбранной строки:

```text
FYP-0412_yoga-mirror_master__lora-2_2026-08-27_1900.mov
FYP-0412_yoga-mirror_master_v2__lora-2_2026-08-27_1900.mp4
PPV-076_anal-yoga_teaser__lora-1_2026-08-30__6m41s.mp4
FYP-0412_yoga-mirror_cap__lora-2_2026-08-27_1900.txt
```

Аккаунт и слот защищают недельную выгрузку от перепутывания и обозначают назначение,
а не фактическую публикацию. Обе формы имени подходят для сверки по правилам SPEC §7:
ID, роль и версия сохраняются, фактические аккаунт и время берутся из Hub.
Подпись выдаётся отдельно; в недельном режиме — sidecar-файлом роли `cap`.
Кастом для фана скачивается под нейтральным именем, например `lora-custom.mp4`.
Исходник и превью с черновика (ID ещё нет) скачиваются под исходным именем файла с
Я.Диска или загрузки; точного совпадения с Hub такое имя не даёт (SPEC §7).

Выгрузка из промо-подборки содержит её номер, порядковый номер файла, ID исходного
объекта с ролью ассета при необходимости и манифест конкретной передачи:

```text
PRM-012_01_FYP-0412.mov
PRM-012_02_SET-069-ed03.jpg
PRM-012_03_PRM-012-clip01.mp4
manifest.csv
```

Расширение соответствует выданному формату: мастер или копия по профилю подрядчика;
последний пример — собственный файл подборки, первые два — из других объектов.
`manifest.csv` фиксирует номер `PRM`, порядок файлов, исходные ID и роли, версии
ассетов, SHA-256 мастеров, профиль подготовки, имена и размеры файлов. Старая
передача использует свой снимок состава и имён даже после изменения подборки.
Имя фана и закрытые поля в пакет не попадают; имя архива не заменяет ключ передачи в БД.

## 7. Альбомы vault

Обычное имя альбома:

```text
ID Название
```

Примеры: `SXT-003 Йога, дилдо, сквирт`, `PPV-069 Анал, йога, гольфы`,
`SET-070 Красное платье, зеркало, отель`.

Правила:

- ID стоит первым; emoji разрешён только в конце.
- Кастом получает альбом только с ID, без имени фана.
- FYP остаётся месячной корзиной `FYP YYYY-MM`.
- LIFE остаётся общей корзиной `Lifestyle`.
- `platform_title` хранится отдельно и может попадать в необязательное описание альбома.
- Английские теги остаются в БД и в название vault не выходят.
- Существующие номера `S1…S7` соответствуют `SXT-001…007` и не меняются.
- До миграции нужно проверить, несут ли другие альбомы PPV-номера, а также фактические
  ограничения длины, поиска и видимости названий.

Основание решения — снимок vault lora-1 от 26.08.2026: чаттер видел название альбома и
число файлов, но не описание и теги; существующий альбом
`💦S3 - Йога, дилдо, сквирт (61)` уже связывал номер секстинга с русскими крючками.

Сопоставление с Hub идёт по SPEC §7–8.1: имя скачивания с ID вместе с длительностью
и размерами либо ручное подтверждение конкретной пары дают точную связь. Аккаунт и
дата в имени для этого не обязательны. Проверка на реальных постах, допуски и
покрытие остаются в SPEC §13. Лимит имени альбома проверяется одним вызовом обновления
на одноразовом альбоме. Скрытые маркеры не используются. Отсутствие связи не означает,
что материал не выходил.

## 8. Telegram, речь и приватность

- В UI, карточках и человеческой речи используются русский язык и короткий ID.
- Модель не обязана получать или писать ID: она продолжает сдавать материал привычными
  словами и длительностями, а систему связывает оператор или автоматизация.
- В речи ведущие нули не произносятся. Текстовый разбор принимает `CUS-183`, `cus183`
  и `#cus183`.
- ID, slug, роли, аккаунты, машинные имена и теги используют латиницу.
- Подписи публикуются на английском и не содержат ID.
- Telegram-карточка заказа не получает публичный ID. Её стабильная внешняя
  идентичность — `tg:<chat>/<topic>/<message_id>`; `CUS` появляется при принятии сдачи.
  Доставка карточки модели остаётся открытым вопросом SPEC §13.
- Реплай модели, текст и имена, разделы источников, идентичность файла, длительность
  и временное окно оцениваются вместе по SPEC §8.2, без фиксированного ранжирования.
  Основание привязки и ссылки сохраняются; противоречия и несколько кандидатов
  подтверждает человек или агент (с пометкой «подтверждено агентом», SPEC §11.1). Одной длительности и близкой даты для автопривязки недостаточно.
- При сдаче система может оставить квитанцию вида `✅ CUS-181 · 13:03 · файл на диске`.
- Чаттер работает в контексте своей модели. Рядом с ID нет копируемого поля с именем
  фана.

Сигналы привычного процесса:

- корень Я.Диска подсказывает тип или назначение, но не определяет идентичность;
- EXIF-день группирует RAW, а при его отсутствии используется временной кластер загрузки;
- `MM:SS` сверяется с длительностью файла; расхождение от пяти секунд становится флагом;
- при связи сдачи с заказом длительность используется односторонне: сдача может быть
  длиннее, но не короче заказанной более чем на 10%;
- `IMG_*`, `copy_*`, `lv_0_*` и `PMR*` — улики камеры, копии iOS, экспорта CapCut или
  вендорской камеры, а не готовая классификация;
- папки `Posted/`, слова `used` и даты продолжают читаться как заявления легаси;
  менять привычную раскладку Я.Диска не требуется. Подтверждённые факты использования
  хранятся как размещения в системе (SPEC §6.3, §7).

Поля исторических карточек и прежние правила сопоставления сохранены в
[«Старый контент и импорт»](legacy-and-import.md#92-сигналы-для-разбора);
действующий контракт заказа и привязки сдачи — SPEC §8.2.

## 9. Проверочный список реализации

- Один разборщик обслуживает каждый класс имени; slug без `_`, роль обязательна.
- Паддинг обеспечивает файловую сортировку, но приложение сортирует номер численно.
- URL объекта содержит модель: `/lora/i/PPV-073`, `/lora/a/PPV-073/master`; маршрута
  к байтам по хэшу без модели нет.
- Уникальность ID обеспечивается ключом `(model, type, number)`; внутренний `uid` не
  выходит в речь и имена.
- На кросс-модельных экранах модель видна в каждой строке. Файл без контекста
  определяется по SHA-256, не по имени.
- Переименование `title_en` (или `title`, если английского названия нет) меняет только
  имя следующего скачивания: ID, URL, блоб, история и резервная копия прежние.
- Один ID проходит через объект, скачивание, vault и операционные карточки; байты
  связываются по SHA-256.
- Новая модель добавляется конфигурацией источников, аккаунтов и собственных рядов ID.
- Новая поверхность добавляется как surface, а не новый класс имени.
- ИИ предлагает метаданные в БД; подтверждение ведётся по полям (SPEC §5).
  Имя каждого скачивания собирается из текущего названия по §4–6.
- Агенты принимают ID и модель, а не файловые пути; каждый исторический путь доступен
  через алиас.
- Запись алиаса сохраняет исходную строку, NFC-нормализацию, ссылку на объект или ассет
  и вид алиаса; поиск учитывает алиасы.
- Для Lily проверяются отдельный источник, аккаунты и ряды с `001`; для Ари — локальная
  папка или веб-загрузка. Общие грамматика, роли и BlobStore не меняются.

## 10. Сквозные примеры

1. **Новая съёмка под PPV.** Модель загружает 34 файла. Система создаёт RAW-пачку,
   Диана выбирает мастер, добавляет тизер и фото, после чего появляется PPV. На Я.Диске
   ничего переименовывать не нужно.
2. **Несколько монтажей из одного сырца.** Один raw-файл становится родителем нескольких
   FYP. Для других страниц система создаёт уникальные версии монтажа — отдельные
   ассеты с происхождением и своими размещениями (SPEC §9.3).
3. **«Это уже публиковалось?»** SHA-256 ведёт к объекту и истории размещений. Если
   мессенджер перекодировал файл, похожий результат остаётся кандидатом до подтверждения.
4. **Кастом становится PPV.** `CUS` хранит сданный материал и версии, связанные с
   отдельным заказом; новый `PPV` связан с кастомом происхождением. Покупатель виден
   в заказе, его имя не подставляется в публикацию PPV.
5. **Промо-подборка.** `PRM` объединяет специально снятые и выбранные существующие
   ассеты в папке канала; файл сохраняет ID источника. Подготовка создаёт выгрузку с
   `manifest.csv`; только отметка «Передано» фиксирует передачу. Повторная передача
   сохраняет номер `PRM`, прошлый манифест и версии файлов остаются в истории.
6. **Недельный планировщик.** Файлы содержат аккаунт и слот, подписи лежат отдельно;
   размещения остаются плановыми до подтверждённого выхода.
7. **Новая модель.** Ей задаются источники, аккаунты и собственные счётчики. Общая
   грамматика и роли не меняются.
8. **Сториз.** Используется существующий ассет и новая поверхность `story@account`;
   нового ID-класса не появляется. Выход отмечает КМ; запись остаётся в плане и
   истории, автосверка не запускается. Для рассылки действует тот же ручной учёт
   (решение 06.09.2026, SPEC §7).

## 11. Зафиксированные решения и открытые границы

Владелец зафиксировал основные развилки 24–27.08.2026:

- три цифры для большинства типов и четыре для FYP, с растущим паддингом;
- отсутствие даты и длительности в каноническом имени;
- поля через `_`, слова slug через `-`, роль обязательна;
- разовый сдвиг PPV выполняет импортёр, а не человек заранее (снято 04.09.2026: ряд не
  двигается, SPEC §6.4);
- `CUS` выдаёт софт при создании заказа (с 02.09.2026 — при приёмке сданного кастома,
  SPEC §4.1);
- ID присутствует в операционных именах, но не в подписях;
- одна RAW-пачка имеет один ID, файлы внутри — под-номера; сохранение типа и
  автоматической нумерации подтверждено 06.09.2026 (SPEC §4.1);
- промежуточный ручной реестр не создаётся;
- LIFE имеет отдельный префикс;
- vault использует `ID Название`, а `platform_title` остаётся отдельным;
- промо-пакет содержит порядковый номер, ID источника и манифест;
- модель не получает новую обязательную папку вроде `0. Новое/`;
- у каждой модели свои ряды ID, а машинный контекст модели обязателен.

Уточнения по прототипу интерфейса, 28.09.2026 (код прототипа — `download-name.ts`,
`download-files.ts` в `packages/contracts/src`, образец — тег `design-1b`):

- **Заменено решением 18.10.2026 ниже:** «slug — транслит по таблице §4;
  английские slug в примерах §6 — иллюстрация»;
- стоп-слова slug — предлоги, союзы и частицы: a, bez, dlya, do, i, ili, iz, k, ko, na,
  nad, ne, no, o, ob, ot, po, pod, pri, pro, s, so, u, v, vo, za;
- аккаунт в имени — код страницы как есть, с несколькими дефисами (`lora-vip-of`);
  группа `account` регулярки §5 читается как `[a-z0-9]+(?:-[a-z0-9]+)+`;
- длительность `__NmSSs` — своя у выданного файла: у мастера — его версии, у тизера —
  тизера;
- кадры сета: «Фото 100 %» — все кадры по съёмке `raw01…`, «Для заливки» — отобранные в
  заданном порядке `ed01…` (обработанный вместо исходного); ничего не отобрано — все
  кадры по съёмке;
- уникальная версия фупа N в строке плана — `_uN`; базовый монтаж без `_uN`;
- архив нескольких файлов называется как его файлы без номера:
  `SET-074_chtenie-knigi-stringi_ed__lora-2_2026-09-22_2000.zip`;
- в архиве дня и недели папки — коды страниц (`lora-2/`, у недели
  `2026-09-22/lora-2/`), кадры лежат отдельными файлами, не архивом в архиве;
- номер файла в ZIP промо — две цифры, при 100 файлах и больше — три
  (`PRM-013_001_RAW-0213-raw03.mp4`).

Решение владельца 18.10.2026: slug строится из короткого английского названия;
транслит русского — только запасной вариант (§4). ИИ предлагает оба названия,
человек или агент утверждает. Английское название хранится, slug — нет: решение
04.09.2026 о вычислении имени при скачивании остаётся в силе.

25.08 английское название уже было предпочтительным источником slug. При упрощении
спеки 04.09 (п. 2, `ad56ade`) slug стал функцией русского названия и перестал
храниться; английская ветка отпала побочно, отдельной развилкой её не обсуждали.
28.09 правило транслита закрепили при согласовании прототипа (`e0704c9`).

Причины выбора английского: удаление предлогов ломает грамматику транслита
(`rubashka-galstukom-igra-grudyu`), лимит в 40 знаков режет смысл, а рядом с
английскими именами легаси диска и хэштегами vault возникает третий язык.
Примеры принятого нейминга:
`PPV-005_dildo-ride-anal-plug-naked_teaser__0m14s.mp4`,
`PPV-011_titfuck-dildo-face-nipple-licking_pic03.jpg`.

Открытые вопросы не закрываются этим reference. Актуальный список находится в
[SPEC §13](../../SPEC.md#13-не-определено).
