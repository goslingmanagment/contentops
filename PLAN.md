# ContentOps — план реализации

План задаёт только порядок работ, зависимости и критерии завершения.
Весь продукт из [PRD](PRD.md) реализуется в одной версии: этапы не являются
продуктовыми волнами и не сокращают итоговый состав.

Порядок принят владельцем 12.09.2026: основа → рабочие процессы и Hub → загрузка
партии библиотеки на winpc → ИИ и автоматизация агентами → обкатка и полная приёмка →
остаток библиотеки и сервер. Полный объём библиотеки (около 1.2 TB) не берётся, пока
всё не проверено и не обкатано на партии (решение владельца 12.09.2026).
ИИ — последний функциональный этап (8): выбор поставщиков, замеры и интеграции
с моделями выполняются там. Этапы 1–7 работают без моделей: поля и поиск доступны,
старые сведения переносит импортёр, КМ дополняет их по необходимости. Полная ручная
разметка библиотеки не требуется для импорта или обкатки. Общий API, права, журнал
и подготовка кадров появляются вместе с соответствующими функциями основы.

Нумерация этапов 1–10 закреплена: на неё ссылаются SPEC и схема данных. Внутри
этапов 1, 2, 4, 8 и 9 выделены подэтапы (1а, 1б, …) с собственными результатом,
зависимостями и критериями завершения (12.09.2026); у этапа 5 — подэтап 5б
(29.10.2026). Подэтап закрывается отдельно;
этап — когда закрыты все его подэтапы и общие условия этапа. Зависимость может
указывать на подэтап.

Технические контракты задаёт [SPEC](SPEC.md). Исходные факты и ограничения
сохранены в [legacy/import](docs/reference/legacy-and-import.md),
[infrastructure](docs/reference/infrastructure.md) и
[compression](docs/reference/compression.md). Открытые вопросы перечислены в конце SPEC;
этот план их не закрывает.

Интерфейс делается вместе с функцией, которой служит. Навигация всего продукта и
пять визуальных образцов — библиотека, карточка, приёмка, план с задачами и сверка
(SPEC §12.0) — фиксируются в подэтапе 1б, до рабочих экранов. Библиотека, карточка и
поиск собираются с каталогом (2а), экран приёмки — с забором (2в), план с задачами —
в 4а, сверка — с Hub (5). Образец — принятый прототип целиком (тег `design-1b`,
`design/DESIGN.md`): остальные экраны, в том числе журнал, настройки и вход, берутся
из него вместе с функцией, которой служат (DESIGN §2.5, §4); отдельного прототипа
на каждый сценарий нет. Приёмка каждого экрана включает внешний вид, поведение и
производительность. Код образца идёт в продукт, но его контракты приводятся к SPEC и
схеме данных (списки значений, поля, коды ошибок, пагинация), а правила, которые в
образце считают заглушка и браузер (например, допустимые места в окне «В план»),
переходят на сервер вместе с тестами: агент по API проходит те же проверки, что КМ.

## Этап 1. Собрать переносимую основу

**Результат:** приложение повторяемо запускается на Linux-профиле любого целевого
хоста; навигация и визуальные образцы утверждены.

**Зависимости:** текущие PRD, SPEC и reference-материалы.

### 1а. Переносимый стек

**Результат:** приложение повторяемо запускается на Linux-профиле любого целевого хоста.

**Готово, когда:**

- Код продукта живёт в этом репо, в корне (решение владельца 30.09.2026): первый PR 1а
  ставит тег `design-1b` на принятый образец и переносит в корень через `git mv`
  `design/apps`, `design/packages` и файлы workspace (`package.json`,
  `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `biome.json`, `.gitignore` — дополненный
  `.env`, `.env.*`, `!.env.example`, `__pycache__/`); `.oxlintrc.json` не переносится;
  в `design/` остаётся `DESIGN.md`.
- При переносе убираются кнопка «Проверить заливку» с маршрутом `:check-upload`
  (решение владельца 30.09.2026), ненастоящие лайки прототипа (настоящие — этап 5,
  решение владельца 29.10.2026), `?variant=pages`, `viteSingleFile` и `base: './'`,
  состояние «мастер сжимается» у PPV-076, сториз в правилах «В план» у сетов и лайфа;
  пустое место заменяется на «нет данных», hash-история — на browser. Заглушка API
  выносится из `packages/contracts` в отдельный пакет для разработки и уходит вместе с
  `?demo`, `?as` и `?skin`, когда экраны по областям переходят на сервер.
- С первого PR CI — GitHub Actions на GitHub-hosted `ubuntu-24.04`: `pnpm check` (типы,
  Biome, тесты, Testcontainers); слияние — после зелёного CI. Тесты, названные в PLAN,
  SPEC и схеме данных §9.4, — норма и пишутся вместе со своим этапом (решение владельца
  29.10.2026).
- Продукт работает в ВМ Hyper-V `contentops` на winpc и ставится в неё из тега
  (SPEC §12.1–12.2): тестовые прогоны до этапа 3 и настоящая база с этапа 3 — в одной ВМ,
  без переезда. Хост к этапу 3 готов: ВМ стартует с Windows без входа и штатно
  выключается при выключении winpc (проверено перезагрузкой), диск превью и
  предзабора — на E:, копия Я.Диска в ВМ только для чтения (`/mnt/ydisk`), доступ —
  через Tailscale. Агенты и тестовые стеки в ВМ не запускаются; разработка — в WSL на
  winpc с потолком 2 GB, сборки и тесты — на Mac и в CI (решение владельца 29.10.2026).
- Единый скрипт запуска поднимает приложение, БД, планировщик и фоновые воркеры.
- Миграции применяются повторяемо в чистом окружении и проверяются автоматически.
  Миграции идут по этапам: этап 1 создаёт 13 таблиц основы (модели, аккаунты,
  поверхности, каналы, люди, права, сессии, токены, счётчики, настройки, работы,
  идемпотентность, журнал), раннер с блокировкой и контрольными суммами, роли БД,
  команду bootstrap и тестовый каркас; остальные таблицы SPEC §4.2 появляются с этапом,
  чей код их пишет (схема данных §9). Структурный тест по каталогу БД проверяет
  `model_id` и составные связи во всех доменных таблицах на каждом этапе.
- Конфигурация и секреты передаются снаружи; прикладной код не зависит от имени,
  адреса или файловой системы конкретного хоста.
- Работают авторизация, healthcheck, структурированные логи и экран «Состояние» с
  фоновыми операциями.
- Первый настоящий путь API (Fastify → БД → клиент) — вход и Настройки, в том числе
  «Люди и доступ» и норма недели, с записью изменений в Журнал (экраны уже есть) —
  проходит тесты SPEC §11.2 на `PUT …/week-norm`: одновременные изменения, одновременные
  повторы, потерянный ответ после сохранения, повтор после отзыва доступа; путь показан
  владельцу скриншотами в отчёте подэтапа.
- Перезапуск или прерывание операции не создаёт повторных записей и задач.
- Исполнитель фоновых работ проверен на настоящем PostgreSQL: два экземпляра одной роли
  одновременно разбирают работы и каждую берут ровно раз, роль не берёт чужие виды;
  после падения процесса работу подхватывают по истечении аренды; устаревшее поколение
  не пишет итог; два планировщика ставят одну строку на интервал; остановка роли
  возвращает работу без счёта попытки.
- Образцы настроек Tailwind 4, Drizzle и Vite «как у нас» — сами конфиги репо;
  `AGENTS.md` ссылается на них одной строкой (SPEC §12.0).
- Реестр выключателей SPEC §8 и глобальная область `policy_settings` есть с миграции
  0001; приложение стартует без секретов выключенных интеграций. Общий сценарий «всё
  выключено» — загрузить, принять, найти, скачать, поставить в план, отметить вручную —
  заводится тестом основы и дополняется шагами по мере появления функций (2а–2в, 4а);
  целиком проходит при закрытии этапа 4 и дальше приёмочный.

**Закрыт 30.10.2026:** PR #2–#7, #9–#11, #13, #14; ВМ `contentops` работает из тега
`v0.1.2` (`/opt/contentops`, `ops/up.sh`), вход владельца, настройки, норма недели и журнал —
на настоящей базе. Хвосты владельца: HTTPS-сертификаты тейлнета (до них `tailscale serve`
по HTTP) и настройка BIOS «Restore on AC power loss»; холодный тест перезагрузки — к этапу 6.

### 1б. Навигация и визуальные образцы

**Результат:** навигация всего продукта и пять образцов утверждены владельцем; рабочие
экраны следующих этапов собираются из них.

**Зависимости:** PRD, SPEC §12.0; от 1а не зависит и идёт параллельно с ним.

**Готово, когда:**

- Зафиксирована навигация всего продукта: разделы, переходы и что видит каждая роль;
  места будущих функций ИИ учтены, ранние экраны работают без них.
- Пять образцов — библиотека, карточка материала, приёмка, план с задачами и
  сверка — сделаны в общем `packages/ui` на рабочих размерах окна: светлая тема по
  образцу веб-Я.Диска, одна акцентная краска, один типографический масштаб, спокойная
  плотность, состояния загрузки, ошибок и пустых результатов; управление с клавиатуры
  и видимый фокус сохранены.
- Разделы: Приехало, Библиотека, План, Журнал. План — вкладки «День», «Неделя»,
  «Сверить»; образец «сверка» — вкладка «Сверить»; задачи на день — План › День.
  Промо — папка Библиотеки, заказы — вид папки «Кастомы». Недельная сводка темпа —
  План › Неделя: пустые места и пропуски в шапке каждой страницы; спорное импорта —
  вкладка «Разбор старого»; отдельного экрана сводки нет.
- Правила поведения SPEC §12.0 показаны на образцах: место под медиа зарезервировано
  до загрузки, возврат из карточки восстанавливает фильтры, выделение и прокрутку,
  фоновое обновление не сбрасывает ввод и несохранённые правки.
- На образцах показаны состояния интеграций «выключено», «не настроено», «временно
  недоступно».
- Образцы утверждены владельцем и с этого момента приёмочные для рабочих экранов.

**Закрыт 28.09.2026:** владелец принял образец `design/` — навигация и экраны в
`design/DESIGN.md`, прототип на стеке SPEC (`apps/web`, `packages/ui`,
`packages/contracts`) на моковых данных; правки нормы внесены. После переноса прототипа
в корень (1а) принятый образец сохраняется тегом `design-1b`.

## Этап 2. Реализовать полный каталог, забор с диска и медиаконвейер

**Результат:** весь контент принимается, обрабатывается и доступен через единое ядро.

**Зависимости:** этап 1 и соответствующие контракты SPEC.

### 2а. Каталог, карточка и поиск

**Результат:** объекты каталога находятся, открываются и скачиваются через API и экраны
библиотеки и карточки; байты хранятся по контракту. До приёмки (2в) объекты заводят
тестовые фикстуры: в продукте объект создаётся только принятием черновика, подборкой
`PRM`, разделением RAW или сменой типа (SPEC §4, §4.1).

**Зависимости:** 1а, 1б.

**Готово, когда:**

- Миграции `0002_bytes_sources` и `0003_catalog` применяются на основу этапа 1 и
  проходят тот же тестовый каркас, включая сгенерированные отрицательные тесты на
  каждую составную связь (схема данных §9).
- Все типы контента из PRD представлены общими механизмами каталога без отдельных
  несовместимых подсистем.
- Работают идентичность, алиасы, происхождение, поиск и проверка согласованности БД
  с хранилищем.
- Источник, сохранённый мастер и производные прослеживаются раздельно по контракту
  SPEC; переименование не меняет идентичность.
- Поля разметки, их версии, происхождение, ручной ввод и поиск работают сразу;
  `annotation_runs` и `annotation_suggestions` — на этапе 8.
- Экраны библиотеки и карточки собраны по образцам 1б: компактный индекс каталога
  модели, фильтры и поиск по названию без запроса к серверу (SPEC §12.0). Поля
  редактируются и подтверждаются отдельно или общей кнопкой; группы тегов сохранены
  при общем вводе. Поиск использует имеющиеся сведения; незаполненные описания и
  хронология видны как незаполненные и не мешают работе с объектом.
- Скачивание из карточки выдаёт готовый файл с именем по SPEC §10 и квитанцией;
  проверяется на готовых файлах и фикстурах. Очистка метаданных и подготовка копий
  принимаются в 2б.

### 2б. Медиаконвейер

**Результат:** принятый файл проверен, сохранён как мастер и получил производные без
вызовов ИИ.

**Зависимости:** миграции `0002` и `0003` (2а), дальше — параллельно экранам 2а.
Кодирование SVT-AV1 обязательно к этапу 3, а не к первому показу.

**Готово, когда:**

- Медиаконвейер выполняет проверки декода, таймингов, кадров и аудио; прерванная
  работа не оставляет наполовину готовых файлов.
- Сохранённый мастер создаётся по SPEC §9.2 и правилам
  [compression](docs/reference/compression.md), включая обязательные проверки и правила
  пропуска; мастера всегда кодируются на CPU. При сбое кодирования мастер — исходник, как
  при `bigger_than_source`; битый исходник, который открывается и дал превью, КМ
  принимает «как есть», нечитаемый ждёт замены в черновике (решение владельца
  30.10.2026).
- Превью, миниатюры, постер и кадры для будущей разметки создаются при приёмке без
  вызовов ИИ одним проходом декодирования; копия для платформы — при постановке в план
  либо первом скачивании; уникальные версии FYP собираются по профилю `uniq`; готовые
  производные используются из кэша (SPEC §9.3). Профиль копии для платформы задан по
  замеру Fansly в Hub `raw_media` (SPEC §13); OnlyFans сверяется, когда Hub отдаст
  размеры OF (этап 5).
- Фото: EXIF и orientation, превью, миниатюра, кадр для разметки и pHash — одна
  идемпотентная задача; HEIC-фикстуры SPEC §12.0 проходят, исходный HEIC не меняется.
- Медиафикстуры генерирует скрипт тестов — без людей и без съёмки (ffmpeg, libheif):
  HEIC 48 МП, повёрнутое фото с EXIF, ролики 4K60 HDR, 120 fps и вертикальный,
  повреждённый файл (решение владельца 30.10.2026). Медиаконвейер проверен и на
  настоящих файлах в ВМ из `/mnt/ydisk` (только чтение; файлы и их имена в git и PR не
  попадают).
- Эталонные ролики конвейера проходят при `ENCODE_JOBS=2`; кодеры не отбирают
  отзывчивость у интерфейса (SPEC §12.0). «Для заливки» без плана при двух занятых
  кодерах собирается на своём месте (`COPY_JOBS=1`); пик памяти замерен и укладывается
  в потолок ВМ 22 GB (решение владельца 30.10.2026).
- Выдача с очисткой метаданных (по умолчанию включена для каждого скачивания,
  SPEC §9.3) и подготовкой копий идёт тем же путём скачивания; квитанция описывает
  выданные байты.
- На машине КМ проверен монтаж сохранённого мастера AV1 10-bit в CapCut; совместимая
  копия H.264 доступна по запросу без постоянного хранения.

**Состояние 30.10.2026:** PR #17, #20, #22, #36, тег `v0.2.1` в ВМ (22 GB, `ENCODE_JOBS=2`).
Конвейер, мастер с проверками, производные из кэша, скачивание с очисткой метаданных и
квитанцией работают; на настоящих файлах в ВМ два AV1 и «Для заливки» рядом дали пик
17,7 GB ([compression](docs/reference/compression.md) §10.9). Копия для платформы — по замеру
Fansly: 1920 по длинной стороне, до 60 кадров/с (§10.10); OnlyFans — на этапе 5. Сборщик
убирает прежние поколения производных (SPEC §9.1). API под двумя AV1 и копией — p95 до 50 мс
против 28 мс на свободной машине (§10.11). Открыто: монтаж мастера AV1 10-bit в CapCut на
машине КМ — проверка владельца (SPEC §13). Экраны под кодированием замерены вместе с
порогами 30.10.2026 ([infrastructure](docs/reference/infrastructure.md) §5).

### 2в. Приёмка с Я.Диска, Dropbox и веба, дубли и заказы

**Результат:** контент попадает в каталог из источника модели — Я.Диска или Dropbox — и
через веб-загрузку повторяемо;
КМ видит черновики и очередь исключений на экране приёмки.

**Зависимости:** 2а, 2б.

**Готово, когда:**

- Миграция `0004_orders` применяется и проходит тот же каркас; приёмка кастома
  привязывается к заказу (схема данных §9.5). Ведение заказов, сдач и правок — 4б.
- Забор из обоих источников — Я.Диск и Dropbox, один интерфейс источника (SPEC §6.1) —
  и веб-загрузка повторяемы; скачивание возобновляется, а готовые файлы регистрируются
  атомарно. Живая проверка — на Dropbox Лоры (туда с 15.10.2026 идёт новое) и на Я.Диске,
  только чтение (решение владельца 30.10.2026).
- Черновик виден с обнаружения, результаты обработки дополняют его по мере
  готовности; непроверенный результат кодирования не принимается (SPEC §6.1).
- Работает поиск дублей: точный дубль по SHA-256 не создаёт второго объекта (кроме пары
  кастом — PPV, SPEC §6.1), источники и пути становятся алиасами; pHash даёт подсказку о
  похожем кадре без автоматического объединения (SPEC §6.2).
- Экран приёмки собран по образцу 1б; неоднозначные случаи остаются в очереди
  исключений с исходными уликами до решения человека или агента.
- Скан источника выключается по источнику (SPEC §8): при выключенном каталог,
  веб-загрузка и обработка уже скачанного работают; включение догоняет без дублей.
- Работа снимка (`scan:freeze`: SHA-256 от API, полнота листинга, оглавления архивов,
  экспорт реестра) готова к первому дню этапа 3 (SPEC §6.3).

**Этап закрыт, когда** закрыты 2а–2в и:

- Репрезентативные образцы, включая дубли, архивы, повреждённые и необычные файлы,
  проходят успешные и ошибочные сценарии без потери исходных фактов.

## Этап 5. Подключить сверку с Hub и проверить API

**Результат:** внешние факты синхронизируются без превращения интеграций в точку отказа;
публикация через Hub — подэтап 5б.

**Зависимости:** 4а (этапа 4 целиком не ждёт), рабочие доступы, контракты источников, Hub
и общего API из SPEC. У ContentOps свой ключ Hub — только страницы его моделей, без
денег; право `read:content` — посты, вложения, медиа и vault без переписки; раньше
этапа 5 ContentOps Hub не читает (решение владельца 29.10.2026). Доработки Hub под
ContentOps (право `read:content`, выдача «изменилось с», отмена своей публикации, стены и
тиры страницы) агент делает сам в репо Hub по его правилам (решение владельца
30.10.2026); сделаны 30.10.2026 (SPEC §8.1).
Внешние входы (решение 11.09.2026, не блокеры этапа):
E1 состояние потоков OnlyFans по страницам (`sync_streams`; при недоступности —
ручной учёт); E2 лимит vault 60 вызовов в день на страницу (снят: на 29.10.2026 vault
lora-1 обойдён целиком); E3 квитанция
загрузки из `fansly-ext` (вне рамок по решению владельца); E4 агентская выдача vault
OnlyFans (чтения в Hub уже идут) и stories OnlyFans (дорожная карта Hub); E5
`capture_coverage` для OnlyFans; E6 закреплённый список нужных полей наборов Hub,
сверяемый по `capabilities` (решение 30.09.2026; смена — согласованное окно); E7 доказательство покрытия постов в Hub
(план `posts` в `capture_coverage` с одним завершённым интервалом на страницу) — без
него автоматическое «не вышло» по постам выключено на обеих платформах. Сториз и
рассылка учитываются вручную независимо от появления данных в Hub; статус сториз,
отправленной через Hub, — в 5б.

**Готово, когда:**

- Проверки на реальных данных lora-1 без записи на платформы (публикация — 5б). V1
  требует человека: КМ заливает файл тремя путями (веб, нативный планировщик,
  мобильный), проверяется, какие из них сохраняют имя файла скачивания ContentOps; пути,
  теряющие имя, остаются на уровне кандидата. V2 и V3 агент считает заранее, до этапа 5,
  по 30 известным постам из данных Hub без участия человека (контракт Hub на них уже
  отвечает): число вложений и роли (жёсткий фильтр по числу для пачек или
  мягкий) и смысл флагов FYP и ссылок стены (поверхность из флагов или от плана и КМ). Точное по видео включается
  (значение `hub_exact_duration_ms`) только после проверки допуска на реальных парах.
- Hub-синхронизация раз в час читает изменения по `rowUpdatedAt` с перекрытием 3 ч (раз в
  сутки — сутки),
  заменяет набор вложений затронутого поста целиком, допускает безопасный повтор и
  полную перечитку при запуске, раз в месяц, после сбоя, rebuild или разрыва; список
  нужных полей сверяется с `capabilities` в каждом прогоне. Публикации без плана сохраняются; «не вышло» по постам
  до E7 не строится (после окна — «не удалось проверить»), по vault — только по
  завершённому обходу альбома после срока (SPEC §7).
- На размещении — подпись с платформы, просмотры и лайки Fansly по каждому файлу по
  дням из Hub (`creator_stats_media_daily`, `creator_stats_media_likes`, с 22.10.2026);
  суточный топ-50 — только для истории до 22.10 (решение владельца 29.10.2026).
- Приёмка на Fansly 1–3 с файлами, выданными ContentOps: посты и заливки набираются,
  пока не будет 15 постов на стене и FYP и 5 заливок в vault, сколько бы дней ни ушло;
  считаются разные файлы, а не повторы по страницам (решение владельца 30.10.2026).
  Каждая заливка по пути, сохраняющему имя, — точное совпадение в пределах окна «ждём»
  от наблюдения; ни одного ложного точного; остальные строки — кандидат в один клик,
  «ждём» или «не удалось проверить» с причиной; p90 задержки постов по монитору внутри
  окна «ждём».
- Приёмка на одной неделе постинга lora-of (решение 13.09.2026): точного по имени на
  OnlyFans нет (SPEC §7); ни одного ложного подтверждения; доля однозначных случаев,
  доля отклонённых кандидатов и время КМ на подтверждение измерены, не обещаны;
  неоднозначное видно и уходит на разбор с указанием источника; подтверждённая пара
  переиспользуется для повторов того же media ID. Доработки Hub — время создания
  медиа и размеры OF в `raw_media`, выдача OF vault (E4) — до недели приёмки, не
  блокеры.
- Отсутствующие и неоднозначные совпадения видимы человеку и разрешаются с указанием
  источника подтверждения.
- История Hub каждой страницы Fansly один раз сопоставлена с каталогом (SPEC §7):
  единственные совпадения — кандидаты без плана, число оставшихся «неизвестно» видно;
  проход повторяется после загрузки партии (этапы 7 и 9а) и «Старого формата» (9б). На
  OnlyFans прохода нет: старое КМ отмечает «Уже залито» пакетом или «Было» (решение
  владельца 30.10.2026).
- Интеграции источников и Hub проходят начальную синхронизацию, повторное
  воспроизведение, обработку лимитов и временных ошибок. Облачные модели и Fyper
  подключаются на этапе 8; рутина заказов `customs-daily` — с 4б.
- API и CLI проверены обычными клиентами: права, изоляция моделей, повтор команд,
  журнал и пометка «подтверждено агентом» у подтверждений агента. Для проверки модель
  не требуется.
- Недоступность одной внешней системы не останавливает независимые рабочие процессы
  и не теряет накопленные для синхронизации события.
- Hub выключается по странице, отдельно получение данных и автосверка (SPEC §8):
  проверены выключение с ожидающей и идущей синхронизацией, перезапуск в выключенном
  состоянии и повторное включение без дублей; выключенный Hub не даёт «не вышло».

### 5б. Публикация через Hub

**Результат:** КМ отправляет строку плана на публикацию из ContentOps, ContentOps
передаёт её в Hub и показывает в строке статус публикации (решение владельца
29.10.2026).

**Зависимости:** сверка этапа 5, поля строки плана из 4а; у ключа ContentOps — права на
черновики, утверждение и отмену своих публикаций. Доработки Hub (отмена своей публикации
ключом-источником до расписания площадки, выдача публикаций «изменилось с») сделаны
30.10.2026 (SPEC §8.1). Этапы 6–8в 5б не ждут, 8г — ждёт.

**Готово, когда:**

- «Подготовить» загружает в Hub недостающие файлы — копию для платформы из мастера с
  именем по naming §5–6 — или передаёт ссылкой точно такой же файл из vault этой
  страницы; Hub создаёт черновик и возвращает свои проверки. «Отправить»: КМ видит
  проверки и подтверждает, ContentOps утверждает публикацию сам; агент по API готовит,
  но не отправляет.
- Стена, FYP, сториз и vault Fansly уходят своими видами Hub (SPEC §7); OnlyFans — посты
  и сториз только файлами из vault, пока владелец не решит про кредиты OnlyFansAPI;
  рассылки — вручную.
- Статусы читаются из Hub раз в 10 мин и видны в строке: «в расписании», «вышло», «не
  вышло: причина», «не удалось проверить — решает владелец в Hub»; связь строки с постом
  точная, через публикацию Hub, без сопоставления.
- Свою публикацию ContentOps отменяет, пока Hub не отправил её в расписание площадки
  (за 7 дней до выхода); позже — только владелец в Hub.

## Этап 7. Загрузить партию библиотеки

**Результат:** партия пилота импортирована, сжата и сверена.

**Зависимости:** этап 6, правило допуска места по SPEC §12.2 по свежему замеру C: и E:
(проверяется перед партией и перед каждой порцией 9а), решение владельца о втором NVMe
на 2 TB под данные пилота (без него место освобождает снятие закрепления проверенных
корней копии, SPEC §12.2) и выполненные условия этапа 3.
Область пилота — вся библиотека, кроме «Старого формата» (этап 9б), но на
этапах 7–8 в каталоге только партия: около половины библиотеки, ориентир 500–600 GB
исходников (решение владельца 12.09.2026; ранее 300–400 GB от 11.09). Состав — по
выбору КМ по всем корням: PPV и секстинги целиком (рабочая необходимость и условия
этапа 3; номера реестра резервируются по метаданным, не по байтам), маленькие корни
(FYP, Sets, BG, Other, Life, Pictures) целиком, из Customs — активные заказы и свежее,
из SMM — экспорты промо по подрядчикам и каналам. Правило связности: цепочки берутся
целиком независимо от свежести — кастом → PPV (14 совпадений байт в байт по
[legacy/import](docs/reference/legacy-and-import.md)), исходник → монтаж → промо,
заказ → сдачи → правки. В партию входят малые представители отложенного: сырьё SMM,
старые кастомы, корневые архивы. Состав фиксируется списком до начала; остальные
ревизии снимка получают состояние «отложено до 9а»: скан их не скачивает, импорт
границу соблюдает, полный проход по метаданным этапа 3 сохраняется. Новые
поступления модели на этапах 7–8 импортируются как обычно — отложен только старый
остаток. Всё отложенное — этап 9а. Разметка старого корпуса — этап 8.

**Готово, когда:**

- Партия импортирована и сжата по SPEC и [compression](docs/reference/compression.md),
  включая обязательные проверки и пропуски; сверка партии со снимком зелёная;
  неоднозначности находятся в управляемой очереди.
- Коллизии старого ряда PPV разрешены по SPEC §6.4, старые метки — алиасы.
- До импорта кастомов агент один раз прошёл старые карточки Customs: заведены заказы с
  покупателем, ТЗ, ссылкой и «имя есть», к ним привязываются кастомы партии и остатка
  (9а) (решение владельца 30.10.2026).
- Проход по истории Hub страниц Fansly повторён (SPEC §7); порог сходства pHash для
  подсказок при приёмке фото задан по партии (SPEC §6.2).
- Собраны фактические метрики объёма, скорости забора и сжатия, ресурсов, свободного
  места, фоновых ошибок и интеграционных задержек.
- Отчёт «можно освобождать» выдаётся по корням, целиком вошедшим в партию и прошедшим
  зелёную сверку.

## Этап 9. Загрузить остаток библиотеки и перенести систему на сервер

### 9а. Остаток библиотеки и полная сверка

**Результат:** вся библиотека пилота, кроме «Старого формата», в каталоге на winpc;
