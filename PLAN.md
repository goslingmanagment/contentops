# ContentOps — план реализации

План задаёт только порядок работ, зависимости и критерии завершения.
Весь продукт из [PRD](PRD.md) реализуется в одной версии: этапы не являются
продуктовыми волнами и не сокращают итоговый состав.

Порядок принят владельцем 12.09.2026: основа → рабочие процессы и Hub → загрузка
партии библиотеки на winpc → ИИ и автоматизация агентами → обкатка и полная приёмка →
остаток библиотеки и сервер. Полный объём библиотеки (у Лоры около 1.45 TB на Я.Диске
по списку копии 30.10.2026; новое с 15.10.2026 идёт в Dropbox) не берётся, пока
всё не проверено и не обкатано на партии (решение владельца 12.09.2026).
ИИ — последний функциональный этап (8): выбор поставщиков, замеры и интеграции
с моделями выполняются там. Этапы 1–7 работают без моделей: поля и поиск доступны,
старые сведения переносит импортёр, КМ дополняет их по необходимости. Полная ручная
разметка библиотеки не требуется для импорта или обкатки. Общий API, права, журнал
и подготовка кадров появляются вместе с соответствующими функциями основы.

Нумерация этапов 1–10 закреплена: на неё ссылаются SPEC и схема данных. Внутри
этапов 1, 2, 4, 8 и 9 выделены подэтапы (1а, 1б, …) с собственными результатом,
зависимостями и критериями завершения (12.09.2026); у этапа 5 — подэтап 5б
(29.10.2026). Подэтап закрывается отдельно;
этап — когда закрыты все его подэтапы и общие условия этапа. Зависимость может
указывать на подэтап.

Технические контракты задаёт [SPEC](SPEC.md). Исходные факты и ограничения
сохранены в [legacy/import](docs/reference/legacy-and-import.md),
[infrastructure](docs/reference/infrastructure.md) и
[compression](docs/reference/compression.md). Открытые вопросы перечислены в конце SPEC;
этот план их не закрывает.

Интерфейс делается вместе с функцией, которой служит. Навигация всего продукта и
пять визуальных образцов — библиотека, карточка, приёмка, план с задачами и сверка
(SPEC §12.0) — фиксируются в подэтапе 1б, до рабочих экранов. Библиотека, карточка и
поиск собираются с каталогом (2а), экран приёмки — с забором (2в), план с задачами —
в 4а, сверка — с Hub (5). Образец — принятый прототип целиком (тег `design-1b`,
`design/DESIGN.md`): остальные экраны, в том числе журнал, настройки и вход, берутся
из него вместе с функцией, которой служат (DESIGN §2.5, §4); отдельного прототипа
на каждый сценарий нет. Приёмка каждого экрана включает внешний вид, поведение и
производительность. Код образца идёт в продукт, но его контракты приводятся к SPEC и
схеме данных (списки значений, поля, коды ошибок, пагинация), а правила, которые в
образце считают заглушка и браузер (например, допустимые места в окне «В план»),
переходят на сервер вместе с тестами: агент по API проходит те же проверки, что КМ.

## Этап 1. Собрать переносимую основу

**Результат:** приложение повторяемо запускается на Linux-профиле любого целевого
хоста; навигация и визуальные образцы утверждены.

**Зависимости:** текущие PRD, SPEC и reference-материалы.

### 1а. Переносимый стек

**Результат:** приложение повторяемо запускается на Linux-профиле любого целевого хоста.

**Готово, когда:**

- Код продукта живёт в этом репо, в корне (решение владельца 30.09.2026): первый PR 1а
  ставит тег `design-1b` на принятый образец и переносит в корень через `git mv`
  `design/apps`, `design/packages` и файлы workspace (`package.json`,
  `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `biome.json`, `.gitignore` — дополненный
  `.env`, `.env.*`, `!.env.example`, `__pycache__/`); `.oxlintrc.json` не переносится;
  в `design/` остаётся `DESIGN.md`.
- При переносе убираются кнопка «Проверить заливку» с маршрутом `:check-upload`
  (решение владельца 30.09.2026), ненастоящие лайки прототипа (настоящие — этап 5,
  решение владельца 29.10.2026), `?variant=pages`, `viteSingleFile` и `base: './'`,
  состояние «мастер сжимается» у PPV-076, сториз в правилах «В план» у сетов и лайфа;
  пустое место заменяется на «нет данных», hash-история — на browser. Заглушка API
  выносится из `packages/contracts` в отдельный пакет для разработки и уходит вместе с
  `?demo`, `?as` и `?skin`, когда экраны по областям переходят на сервер.
- С первого PR CI — GitHub Actions на GitHub-hosted `ubuntu-24.04`: `pnpm check` (типы,
  Biome, тесты, Testcontainers); слияние — после зелёного CI. Тесты, названные в PLAN,
  SPEC и схеме данных §9.4, — норма и пишутся вместе со своим этапом (решение владельца
  29.10.2026).
- Продукт работает в ВМ Hyper-V `contentops` на winpc и ставится в неё из тега
  (SPEC §12.1–12.2): тестовые прогоны до этапа 3 и настоящая база с этапа 3 — в одной ВМ,
  без переезда. Хост к этапу 3 готов: ВМ стартует с Windows без входа и штатно
  выключается при выключении winpc (проверено перезагрузкой), диск превью и
  предзабора — на E:, копия Я.Диска в ВМ только для чтения (`/mnt/ydisk`), доступ —
  через Tailscale. Агенты и тестовые стеки в ВМ не запускаются; разработка — в WSL на
  winpc с потолком 2 GB, сборки и тесты — на Mac и в CI (решение владельца 29.10.2026).
- Единый скрипт запуска поднимает приложение, БД, планировщик и фоновые воркеры.
- Миграции применяются повторяемо в чистом окружении и проверяются автоматически.
  Миграции идут по этапам: этап 1 создаёт 13 таблиц основы (модели, аккаунты,
  поверхности, каналы, люди, права, сессии, токены, счётчики, настройки, работы,
  идемпотентность, журнал), раннер с блокировкой и контрольными суммами, роли БД,
  команду bootstrap и тестовый каркас; остальные таблицы SPEC §4.2 появляются с этапом,
  чей код их пишет (схема данных §9). Структурный тест по каталогу БД проверяет
  `model_id` и составные связи во всех доменных таблицах на каждом этапе.
- Конфигурация и секреты передаются снаружи; прикладной код не зависит от имени,
  адреса или файловой системы конкретного хоста.
- Работают авторизация, healthcheck, структурированные логи и экран «Состояние» с
  фоновыми операциями.
- Первый настоящий путь API (Fastify → БД → клиент) — вход и Настройки, в том числе
  «Люди и доступ» и норма недели, с записью изменений в Журнал (экраны уже есть) —
  проходит тесты SPEC §11.2 на `PUT …/week-norm`: одновременные изменения, одновременные
  повторы, потерянный ответ после сохранения, повтор после отзыва доступа; путь показан
  владельцу скриншотами в отчёте подэтапа.
- Перезапуск или прерывание операции не создаёт повторных записей и задач.
- Исполнитель фоновых работ проверен на настоящем PostgreSQL: два экземпляра одной роли
  одновременно разбирают работы и каждую берут ровно раз, роль не берёт чужие виды;
  после падения процесса работу подхватывают по истечении аренды; устаревшее поколение
  не пишет итог; два планировщика ставят одну строку на интервал; остановка роли
  возвращает работу без счёта попытки.
- Образцы настроек Tailwind 4, Drizzle и Vite «как у нас» — сами конфиги репо;
  `AGENTS.md` ссылается на них одной строкой (SPEC §12.0).
- Реестр выключателей SPEC §8 и глобальная область `policy_settings` есть с миграции
  0001; приложение стартует без секретов выключенных интеграций. Общий сценарий «всё
  выключено» — загрузить, принять, найти, скачать, поставить в план, отметить вручную —
  заводится тестом основы и дополняется шагами по мере появления функций (2а–2в, 4а);
  целиком проходит при закрытии этапа 4 и дальше приёмочный.

**Закрыт 30.10.2026:** PR #2–#7, #9–#11, #13, #14; ВМ `contentops` работает из тега
`v0.1.2` (`/opt/contentops`, `ops/up.sh`), вход владельца, настройки, норма недели и журнал —

**Результат:** навигация всего продукта и пять образцов утверждены владельцем; рабочие

**Зависимости:** PRD, SPEC §12.0; от 1а не зависит и идёт параллельно с ним.

**Готово, когда:**

- Зафиксирована навигация всего продукта: разделы, переходы и что видит каждая роль;
  места будущих функций ИИ учтены, ранние экраны работают без них.
- Пять образцов — библиотека, карточка материала, приёмка, план с задачами и
  сверка — сделаны в общем `packages/ui` на рабочих размерах окна: светлая тема по

  плотность, состояния загрузки, ошибок и пустых результатов; управление с клавиатуры

- Разделы: Приехало, Библиотека, План, Журнал. План — вкладки «День», «Неделя»,
  «Сверить»; образец «сверка» — вкладка «Сверить»; задачи на день — План › День.

  План › Неделя: пустые места и пропуски в шапке каждой страницы; спорное импорта —
  вкладка «Разбор старого»; отдельного экрана сводки нет.

  фоновое обновление не сбрасывает ввод и несохранённые правки.
- На образцах показаны состояния интеграций «выключено», «не настроено», «временно

- Образцы утверждены владельцем и с этого момента приёмочные для рабочих экранов.

## Этап 2. Реализовать полный каталог, забор с диска и медиаконвейер

### 2а. Каталог, карточка и поиск

**Результат:** объекты каталога находятся, открываются и скачиваются через API и экраны
библиотеки и карточки; байты хранятся по контракту. До приёмки (2в) объекты заводят
тестовые фикстуры: в продукте объект создаётся только принятием черновика, подборкой
`PRM`, разделением RAW или сменой типа (SPEC §4, §4.1).

**Зависимости:** 1а, 1б.

**Готово, когда:**

- Миграции `0002_bytes_sources` и `0003_catalog` применяются на основу этапа 1 и
  проходят тот же тестовый каркас, включая сгенерированные отрицательные тесты на

- Все типы контента из PRD представлены общими механизмами каталога без отдельных
  несовместимых подсистем.
- Работают идентичность, алиасы, происхождение, поиск и проверка согласованности БД
  с хранилищем.
- Источник, сохранённый мастер и производные прослеживаются раздельно по контракту
  SPEC; переименование не меняет идентичность.
- Поля разметки, их версии, происхождение, ручной ввод и поиск работают сразу;
  `annotation_runs` и `annotation_suggestions` — на этапе 8.
- Экраны библиотеки и карточки собраны по образцам 1б: компактный индекс каталога

- Скачивание из карточки выдаёт готовый файл с именем по SPEC §10 и квитанцией;
